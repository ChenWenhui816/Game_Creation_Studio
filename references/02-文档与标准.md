# P1 文档与标准：把一页纸变成可判定的标准书

> 适用阶段：P1（第 2–3 周） ｜ 何时加载：G0 已过，要开工白模或美术生产之前 ｜ 上游：`references/01-立项.md`（立项书） ｜ 下游：`references/03-美术资产管线.md`、`references/04-引擎实现.md`

## 这一阶段要回答的问题

1. 每个系统“做完”的定义是什么？谁看、看什么、几秒能判定？
2. 玩家身高、跳跃高度、跑速、相机这几把尺定在哪，其余参数怎么推导？
3. 数值到底存在哪个文件？为什么不能写两处？
4. 资产清单 16 列每列填什么，状态怎么流转？
5. 什么改动必须走变更单，口头需求怎么处理？
6. 两次评审各 1.5 小时，具体看什么、你只回答哪几种话？

## 步骤

### 步骤 2：把每条标准写成“可判定”

每条标准只有两种合格写法，其他一律删：

- **机器可查**：脚本能直接验（面数、命名、色板、帧数、数值区间）。
- **人眼 3 秒可判**：你盯着截图/录屏 3 秒能说“合格/不合格”（构图、光照方向、镜头高度）。

写之前问三个问题：**谁能判？判什么？几秒判完？** 三个都答不上来，这条标准作废。

#### 正反例 1：资产与美术（8 组）

| 维度 | 反例（不可判定） | 正例（可判定） | 判定方式 |
|---|---|---|---|
| 面数 | “模型面数要低” | 主角 ≤15,000 三角面；杂兵 ≤5,000；场景模块 ≤8,000 | 导出时脚本统计三角面 |
| 贴图 | “贴图要清晰” | 角色 2048×2048、场景 1024×1024、UI 512×512；只用 2 的幂 | 资源命名 + 脚本读尺寸 |
| 材质粗糙度 | “金属要真实” | Roughness 0.35 ±0.05，Metallic 0.9；参数名固定为 `M_Rough` | 材质实例数值，人眼可判 |
| 动画帧数 | “动作要流畅” | 跑步 1 秒循环 @24 fps；攻击 0.4 s 共 18 帧；过渡 ≤0.15 s | 动画资产读帧数 |
| LOD | “远处要优化” | LOD0 100%、LOD1 ≤50%、LOD2 ≤20%；切换距离 15 m / 30 m | Static Mesh LOD 设置 |
| 命名 | “命名要规范” | 前缀 SM_/SK_/M_/T_/ABP_/FX_ + 大驼峰 + 下划线；无中文、无空格，如 `SM_Crate_A` | 正则脚本扫描 |
| 色板 | “颜色要统一” | 主色 5 个 hex + 辅色 3 个 hex，禁止色板外颜色（容差 ±3/255） | 逐像素脚本比对 |
| 碰撞 | “碰撞要贴合模型” | 主角胶囊半径 0.4 m、半高 0.9 m；场景用盒体碰撞，凸包 ≤32 顶点 | 编辑器碰撞视图 + 数值 |

#### 正反例 2：系统与表现（7 组）

| 维度 | 反例（不可判定） | 正例（可判定） | 判定方式 |
|---|---|---|---|
| 跳跃 | “跳得高一点” | 跳跃高度 2.2 m；到顶点 0.4 s；起跳速度 11 m/s | `numbers check` + 白模实测 |
| 相机 FOV | “视角要舒服” | 水平 FOV 75°；SpringArm 3.5 m、相机高约 2.5 m、俯角 -10° | 相机参数截图 |
| UI 字号 | “字要看得清” | 1080p 下正文 ≥24 px、按钮 ≥28 px、字幕 ≥32 px；对比度 ≥4.5:1 | 截图按像素量 |
| 性能 | “性能要流畅” | 1080p 60 fps：GPU 帧 ≤12 ms；draw call ≤2000/帧；可见三角面 ≤200 万；贴图内存 ≤1.5 GB | Unreal Insights / `stat` 类命令 |
| 加载 | “加载要快” | 单关首载 ≤15 s（SSD）；检查点重载 ≤3 s | 自动化日志计时 |
| 音效响度 | “音效要有冲击力” | 短音效峰值 -6 dBFS；BGM -18 LUFS；主输出 -1 dBTP | 音频表测 |
| 打击反馈 | “打击感要强” | 命中 hitstop 4 帧；震屏 0.15 s / 0.5°；受击闪白 2 帧 | 逐帧看录屏 |

#### 形容词的代价（为什么这一步不能省）

反例：“画面要有氛围感。” → agent 出 3 版你都不满意，第 3 周返工，美术圣经仍没数。
正例：“主光色温 4500 K，从角色右后上方 45° 打；雾密度 0.02；远景饱和度 -20%。” → 一眼能判，且能变成生成与打光参数。

> 【示例】相机 FOV 75 是 16:9 下的水平 FOV；UE 的 FieldOfView 填的是水平值，垂直值随宽高比变化，具体口径以 UE 官方文档与实测为准：https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-documentation

### 步骤 3：立三把尺，其余参数全部推导

先定 3 个数，其他全部由公式算出，不许手调。3D 项目的尺必须写成米（UE 内部是厘米，表格里换算）。

| 尺 | 值 | 为什么是这个数 | 谁能改 |
|---|---|---|---|
| 角色身高 | 1.8 m（含鞋；胶囊半高 0.9 m、半径 0.4 m） | 世界尺度基准：门高 2.2 m、台阶 0.3 m、平台厚 0.4 m 都由它推 | 变更单 |
| 跳跃高度 | 2.2 m（1.22 身位），到顶点 0.4 s | 手感假设，白模只校准这两个数 | 变更单 |
| 跑速 | 6 m/s（3.33 身位/秒） | 关卡长度、相机跟随、跳跃距离分母 | 变更单 |

推导公式与 UE 填写值：

| 参数 | 公式 | 结果 | UE 里怎么填 |
|---|---|---|---|
| 重力 g | g = 2h / t² | 2×2.2 / 0.4² = 27.5 m/s² | 二选一：改项目设置 Default Gravity Z = -2750 cm/s²；或保留 -980 并设 GravityScale = 2.80。不要两处同时改 |
| 起跳速度 v | v = 2h / t | 2×2.2 / 0.4 = 11 m/s | JumpZVelocity = 1100 cm/s |
| 空中总时长 T | T = 2t（上下对称） | 0.8 s | 由上面两项决定，不要另填 |
| 水平跳跃距离 d | d = 跑速 × 2t | 6 × 0.8 = 4.8 m | 关卡空档取 3.5–4.2 m（留 12%–27% 余量） |
| 平台厚度 | ≥0.22 身位 | ≥0.4 m | 灰盒模块统一 0.4 m |
| 门洞高 | ≥1.22 身位 | ≥2.2 m | 场景模块统一 2.4 m |
| Coyote time | 固定手感参数 | 0.10 s | CharacterMovement 的落地宽限，代码实现 |
| 跳跃缓冲 | 固定手感参数 | 0.10 s | 落地前 0.1 s 按跳也生效 |
| 空中控制 | 固定手感参数 | 0.60 | AirControl 0.6（1.0 太飘，0 太硬） |
| 相机 FOV | 固定镜头参数 | 水平 75° | SpringArm 3.5 m、相机高约 2.5 m、俯角 -10° |

> 口径：`d = 跑速 × 2t` 是水平覆盖距离的起点（不含冲刺）；`v = 11 m/s` 是垂直起跳速度，**不能**拿来算水平距离。白模实测水平位移若明显小于设计空档（例如 4.2 m 空档跳不过去），先调助跑/冲刺或缩小空档，**不许改跳跃高度**。UE 里 `JumpZVelocity` 与 `GravityScale` 的组合还受跳跃/下落分段重力影响，公式只作起点，实测值回写 `06_数值表.csv`。

#### 填错会怎样（5 个真实症状）

| 参数 | 常见填错 | 后果 | 可观测症状 |
|---|---|---|---|
| 重力 g | 直接用 9.81（真实重力） | 滞空 1.34 s，角色像在月球 | 起跳后 0.8 s 还没落地 |
| JumpZVelocity | 手调 1500 cm/s | 跳 4.1 m，能跳过设计好的墙 | 玩家从教学关侧墙翻出去 |
| GravityScale | 只改跳速不改重力 | 高度对了，落地时间不对，操作不跟手 | 上升 0.4 s、下落 0.7 s |
| 跑速 | 按“爽”调到 8 m/s | 相机跟丢、跳距超上限、空档全失效 | 玩家频繁冲过头掉下去 |
| 相机 FOV | 用 60°（省性能） | 空间被压扁，落点看不清 | 试玩者在空档前反复停下观察 |

### 步骤 4：数值只能活在一个地方

唯一数值源：`docs/06_数值表.csv`（固定表头 `category,key,value,unit,formula,source,note`）。GDD、美术圣经、技术方案**只引用 key，不写值**。

| 写法 | 例子 | 判定 |
|---|---|---|
| 反例（在 GDD 里写死） | “跳跃高度 2.2 m” | 白模后改成 2.4 m，GDD 仍写 2.2；美术按 2.2 做门高，全崩 |
| 正例（引用） | “跳跃高度见 `06_数值表.csv` 的 `move.jump.height`” | 改一处，全局生效 |

四条硬规则：

1. key 用 `域.对象.属性`，如 `move.jump.height`、`combat.player.hp`、`camera.fov`；同一 key 只出现一次。
2. 派生值必须在 `formula` 列写公式，如 `formula=2*h/t^2`，脚本按公式复算，误差 >0.5% 报错。
3. `unit` 必填（m / m·s⁻¹ / m·s⁻² / s / 帧 / % / px）；UE 用 cm 时在 `note` 写换算。
4. 改值只能走变更单，`source` 列写变更单编号。

```csv
category,key,value,unit,formula,source,note
move,jump.height,2.2,m,,,h=2.2 起跳高度（示例）
move,jump.apex_time,0.4,s,,,到顶点时间
move,gravity,27.5,m/s^2,2*jump.height/jump.apex_time^2,示例,UE GravityScale=2.80
move,jump.velocity,11,m/s,2*jump.height/jump.apex_time,示例,JumpZVelocity=1100 cm/s
move,run.speed,6,m/s,,示例,3.33 身位/秒
camera,camera.fov,75,deg,,示例,水平 FOV
```

同步链（单向，禁止反向手改）：

```text
docs/06_数值表.csv → 导入脚本 → UE DataTable → 运行时读取
        │
        └→ GDD 只写 key（文档渲染时读 CSV）
```

`python scripts/gamecheck.py numbers check --root .` 校验：表头、重复 key、公式复算、单位缺失、GDD 里出现裸数字。

### 步骤 5：资产清单 16 列与状态流

固定表头（不得增删列，扩展写进 `note`）：
`id,type,name,usage,source,file,faces,textures,materials,animations,lod,collision,license,owner,status,note`

| 列 | 含义 | 合法值 / 格式 | 谁填 |
|---|---|---|---|
| id | 唯一编号 | `A0001` 递增，永不复用 | agent |
| type | 资产类型 | char / enemy / boss / env / prop / ui / fx / anim | agent |
| name | 资产名 | 与 UE 资源名一致，前缀见美术圣经 | agent |
| usage | 用在哪 | `关卡名/系统名` | agent |
| source | 来源 | `AI生成/手工/商店购买（含许可）` | agent |
| file | 文件路径 | `art/Export/...` 或 `assets/...` | agent |
| faces | 三角面数 | 整数；char ≤15000 | agent |
| textures | 贴图规格 | `2048x2048` 多条用分号 | agent |
| materials | 材质数 | 整数 | agent |
| animations | 动画数 | 整数；char 12 套 | agent |
| lod | LOD 级数 | 2 / 3 | agent |
| collision | 碰撞类型 | capsule / box / convex / none | agent |
| license | 许可 | `自有/AI可商用-模型名/CC0` | agent |
| owner | 负责人 | 你 / agent | agent |
| status | 状态 | 5 个合法值，见下表 | 唯一状态字段 |
| note | 备注 | 偏差、变更单号 | agent |

状态流（只允许这 5 个值，其他拼写一律报错）：

| 状态 | 进入条件 | 谁能改 | 退出条件 |
|---|---|---|---|
| 待做 | 清单已登记，尚无文件 | agent | 开始制作 |
| 制作中 | 有 `file` 且已有一版 | agent | 提交验收 |
| 待验收 | 规格列填全，有截图 | agent | 你签验收单 |
| 已通过 | 验收单结论“通过” | 你/指定 agent | 入库 |
| 已入库 | 文件在 `assets/` 且游戏内可见 | agent | 废弃（写 note 原因） |
| 废弃 | 需求取消或质量不达标 | 你 | 终态，不删行 |

三条铁律：**清单里没有的资产不许做**；一个 `id` 只对应一个最终文件；`faces/textures/status` 不许空。

### 步骤 6：变更管理

必须走变更单的 5 类改动：

| 类型 | 判定阈值 | 例子 |
|---|---|---|
| 改范围 | 任何关卡/敌人/系统数量的增减 | 3 关改 4 关；砍掉攀爬 |
| 改数值 | 06 表任一行的 value 变化 | 跳跃 2.2 → 2.4 m |
| 改风格 | 色板、主光、比例、命名规则任一变化 | 主色从冷灰改暖橙 |
| 改管线 | 影响 >1 天工作量的技术/导入改动 | 换绑定方案、改贴图压缩 |
| 改已验收内容 | 影响 ≥1 件“已通过”资产 | 主角模型重做 |

变更单要素见 `templates/09_变更单.md` 的 8 章：基本信息 / 现状 / 变更内容 / 原因 / 影响评估 / 选项 / 决策 / 执行清单。每个变更单必须有 **3 个选项**，其中一个是“不改”，每个选项写清“增加几天、砍掉什么”。

**联动校验（v0.2 起强制）**：

1. 变更单编号统一写 `CO-<三位数字>`（如 `CO-001`）；文件名与正文至少一处出现。
2. 「影响评估」必须列一张“影响资产”表（资产 ID / 变更类型 / 变更后状态 / 验收单），或明确写“无资产影响”。
3. 资产清单对应行的 `source` 或 `note` 写该变更单编号；一个资产可关联多张变更单。
4. 归档前跑 `python scripts/gamecheck.py change check --root .`：变更单引用的资产必须存在，清单引用的编号必须有对应变更单。

**口头需求无效**：聊天里出现的任何“我觉得应该……”都先记进周报“待决策”，当天转成变更单；没进变更单的需求，agent 不执行。三句标准话术：

- “这句话我先记成变更单，评估完给你 A/B/C 三个选项。”
- “改这个要动 2 个已做关卡，先确认砍掉哪个来换。”
- “标准书现在是 v1.2，改完变 v1.3，我会把受影响关卡标‘待复验’。”

流程：

```mermaid
flowchart LR
  A[提出需求] --> B[24h 内出影响评估]
  B --> C[3 个选项 A/B/C<br/>含“不改”]
  C --> D[你 30 分钟内选一个]
  D --> E[执行 + 回写标准书]
  E --> F[复跑 gate spec]
  F --> G[变更记录追加一行]
```

### 步骤 7：评审协议（2 次 × 1.5 小时）

| 场次 | 时间 | 看什么 | 产出 | 你只回答 |
|---|---|---|---|---|
| 第 1 次 | 第 2 周末 | 逐条删形容词；抽 15 组正反例对表 | 改完的 GDD/美术圣经/技术方案 | 合格 / 不合格 / 改哪里 |
| 第 2 次 | 第 3 周末 | 06 数值表 8–12 行；资产清单 16 列与数量；性能预算 6 个数字 | 冻结版本号 + 冻结日期 | 合格 / 不合格 / 改哪里 |

第 1 次评审的机械操作：全文搜索这 8 个词，每命中一处就改成数字或删掉：**尽量、适当、差不多、好看、流畅、自然、丰富、合理**。

禁止句与改写示例：

| 你可能会说 | 为什么不合格 | 改成 |
|---|---|---|
| “感觉不太对” | 无法定位，agent 只能猜 | “第 3 关第 2 段空档 4.5 m，超过 4.2 m 上限” |
| “再优化一下” | 没有验收标准 | “主角材质 Roughness 现在是 0.6，标准是 0.35±0.05” |
| “风格再统一一点” | 形容词 | “这版主色偏蓝，色板要求 3 号色 `#2B3A42`” |
| “就这样吧” | 等于放弃评审 | 明确写“合格，冻结 v1.0” |

评审会前 agent 必须交“变更清单”（改了哪些条、每条从什么改成什么），不许口头介绍 15 分钟。

## 反模式

| 表现 | 后果 | 对策 |
|---|---|---|
| 标准书写成 30 页，没人读第二遍 | G1 靠感觉过，P2 之后全在猜 | 每份 ≤12 页；一屏内能查到任何一条 |
