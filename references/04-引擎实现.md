# P2–P4 引擎实现：从白模到可打包的 UE5 工程

> 适用阶段：P2–P4（第 3–22 周） ｜ 何时加载：第一次打开 UE 前、每次改角色手感/系统架构/打包配置前 ｜ 上游：`references/02-文档与标准.md`（技术方案与数值表已定稿）、`references/03-美术资产管线.md`（资产已导入并验收） ｜ 下游：`references/05-打磨与Demo上线.md`（P5 打磨与上线）

## 这一阶段要回答的问题

1. 新建工程时选哪个模板、开哪些插件、定什么目录和前缀，才能 3 个月后（50 天没打开）还不乱？
2. 角色从按下跳跃键到落地，每一毫秒由哪 8 个参数决定？为什么是 2.2 m / 0.4 s / g=27.5 / v=11，改一个会连带改什么？
3. 哪个系统先写 C++、哪个先用蓝图、什么情况下才允许拆成独立插件？
4. 白模的“尺规”是多少？怎么在 2 小时内用 5 个人盲测出一个可信结论？
5. 1080p/60fps 的 16.6 ms 怎么分给 CPU、GPU、VRAM、draw call？超预算时按什么顺序砍？
6. 打包命令、MCP 自动化的边界、Git LFS 规则定到什么程度就可以停手不再改？

## 步骤

### 三轮迭代总表

用户原始流水线是 9 环：技术底座 → 白模 → 系统 → 测试 → 高模替换 → 玩法 → 光影 → 关卡 → 打包。一次性串行走完，在第 5 环就会因为“手感不对”回头重做前 4 环。**改成 3 轮，每轮都是一个能跑、能给人玩的构件的闭环。**

| 轮次 | 阶段/周 | 目标 | 原流水线环节落在哪 | 完成标志 |
|---|---|---|---|---|
| 第 1 轮 | P2 / 第 3–6 周 | 工程能跑、角色手感达标、1 关白模可玩 | 技术底座（步骤 1–3）、角色（4–8）、白模（9）、测试（10） | G2 通过 |
| 第 2 轮 | P3 / 第 6–12 周 | 系统齐全、垂直切片成型、高模替换完成 | 系统（11–19）、高模替换（20）、玩法与光影（21–23） | G3 通过 |
| 第 3 轮 | P4 / 第 13–22 周 | 批量关卡、性能达标、可重复打包 | 关卡（24–25）、性能（26）、打包（27–29） | G4 通过 |

三条硬规则（违反任一条，第 3 轮必然崩）：

1. **每轮末尾必须能出包**：Development 配置打成可运行的 exe，哪怕只有 1 关。出不了包的轮次不算完成。
2. **每轮只允许一类大改**：第 1 轮只改角色与空间，第 2 轮只改系统与美术，第 3 轮只改性能与内容量。混着改，出问题无法归因。
3. **高模替换只在第 2 轮做一次**：替换后不再回头改白模布局；确需改布局 → 走 `templates/09_变更单.md`。

> 时间不够时按此顺序砍：第 3 轮的关卡数 → 第 2 轮的 VFX 数量 → 第 1 轮的白模关卡数（保 1 关）。**永远不砍第 1 轮的手感参数与第 3 轮的打包流程。**

### 第 1 轮（P2）：工程底座 + 角色 + 白模

#### 步骤 1：新建工程与插件（半天）

| 项 | 选定值 | 说明 |
|---|---|---|
| 引擎 | UE 5.8（锁定到次版本号，写进 `gamecheck.json`） | 两个引擎版本交替打开会把资产降级；团队只有 1 人时更危险 |
| 模板 | Third Person | 自带 Character、SpringArm、Enhanced Input 映射，省 1 天；不要用空白模板从零搭 |
| 工程路径 | 全英文、无空格、不在 OneDrive/网盘/中文目录 | UE 对中文路径与云同步盘会随机报错，报错信息没有指向性 |
| 目标硬件 | Desktop | 不要勾 Mobile/Console，插件与渲染管线会被裁掉 |
| RHI | DirectX 12 | Lumen/Nanite 需要 DX12 或 Vulkan SM6 |

插件开关（**开**）：Editor Scripting Utilities、Modeling Tools Editor Mode、Geometry Script、Common UI、MetaSound、Animation Warping、Control Rig。
插件（**保持关闭**）：Water、Landmass、Pixel Streaming、Gameplay Ability System（技能 ≤8 个时用枚举 + 蓝图实现更快）、Online Subsystem（只在要成就/云存档时开，见 P5）。
每多开 1 个未用插件，打包时间约 +1–5 分钟，且增加 cook 失败面。

#### 步骤 2：项目设置（必改 6 项，改完存成模板）

| 设置路径 | 值 | 为什么 |
|---|---|---|
| Maps & Modes → Default GameMode | BP_GameMode_Game | 新建关卡不手动改就是对的 |
| Maps & Modes → Editor Startup Map | L_Sandbox | 打开 UE 直接进白模，省掉每天 2 分钟找文件 |
| Physics → Default Gravity Z | -2750（cm/s²） | 即 g=27.5 m/s²；UE 单位是厘米 |
| Rendering → Dynamic Global Illumination | Lumen | 与 P3 光影阶段一致，避免中途切换重打光 |
| Rendering → Auto Exposure | 关闭，固定 EV100 | 自动曝光让“这关暗不暗”不可复现，盲测结论会失真 |
| Packaging → Use Pak File / Share Material Shader Code | 都勾 | 减小首包体积，减少 shader 编译 |

固定编辑器帧率上限 60（t.MaxFPS 60）：编辑器里跑到 200 fps 会掩盖真实的性能问题，等到打包才发现掉帧。

#### 步骤 4：Enhanced Input（半天）

| 资产 | 映射 | 备注 |
|---|---|---|
| IMC_Default | W/S/A/D、左摇杆 → IA_Move（Axis2D） | 死区 0.2 |
| IMC_Default | 鼠标 X/Y、右摇杆 → IA_Look（Axis2D） | 鼠标灵敏度 0.5，摇杆 0.7 |
| IMC_Default | 空格 / 手柄下键 → IA_Jump | 用 Started 触发，别用 Triggered（会连跳） |
| IMC_Default | Shift / 左摇杆按下 → IA_Sprint | Toggle 或 Hold 二选一，写进 GDD |
| IMC_Default | E / 手柄右键 → IA_Interact | 需要“按住 0.3 s”时加 Hold 触发器 |
| IMC_Default | 鼠标左键 / 手柄右键 → IA_Attack | 与 Interact 共键时用不同 IMC 隔离 |

三条纪律：

1. 输入只在 Character/PlayerController 里消费，**不写进 UI 和动画蓝图**。
2. 打开菜单/过场时用 SetInputModeUIOnly 或 CommonUI 自带焦点管理阻断移动，不要靠“加个 bool 就 return”。
3. 不用 IsInputKeyDown 轮询；Enhanced Input 的 Started/Completed 才是唯一入口。

#### 步骤 5：角色与相机参数（先写表，再进引擎）

**先给数字，再动手**。下表每个数字都必须能在 `docs/06_数值表.csv` 里找到同名行；表里没有的，不允许出现在编辑器里。

| 参数 | 值 | UE 字段（注意单位） | 推导与说明 |
|---|---|---|---|
| 跳跃高度 h | 2.2 m | — | 角色身高 1.8 m 的 1.22 倍：能跳上 2 m 台，留 0.2 m 冗余 |
| 到顶点时间 t | 0.4 s | — | 0.35 s 太急、0.5 s 太飘；0.4 s 是平台跳跃的“脆感”档 |
| 重力 g | 27.5 m/s² | 项目设置 Default Gravity Z = -2750 cm/s² | g = 2h/t² = 2×2.2/0.4² = 27.5（约为默认 9.8 的 2.8 倍） |
| 起跳速度 v | 11 m/s | JumpZVelocity = 1100（cm/s） | v = 2h/t = 2×2.2/0.4 = 11；UE 用厘米，故填 1100 |
| 跑步速度 | 6 m/s | MaxWalkSpeed = 600（cm/s） | 6 m/s 是“跑得比人快一点但不失控”；走路档 250 |
| 空中控制 | 0.6 | Air Control = 0.6 | 0 = 空中不能转向（硬），1 = 与地面等同（飘）；0.6 是折中 |
| 土狼时间 | 0.1 s | 自定义变量 CoyoteTime | 离开平台后 0.1 s 内按键仍起跳；>0.2 s 会被玩家感知为“延迟奇怪” |
| 跳跃缓冲 | 0.1 s | 自定义变量 JumpBufferTime | 落地前 0.1 s 内按跳，落地立即起跳 |
| 相机 FOV | 75° | Camera → Field of View | 90 有桶形畸变，60 看不到脚下；第三人称常用 70–80 |
| 弹簧臂长度 | 350 cm | SpringArm → Target Arm Length | 3.5 m；角色在画面中约占高度 1/4 |
| 相机延迟 | 0.12 s | SpringArm → Camera Lag Speed ≈ 8.3 | UE 没有“延迟秒数”字段，用 1/0.12 ≈ 8.3 起步，再按实测微调 |
| 转身速度 | 540°/s | CharacterMovement → Rotation Rate | 0.67 s 转半圈；配合“朝移动方向旋转”的 bOrientRotationToMovement |

三条自洽检查（改任何一个就重算一次）：

1. `g = 2h/t²`：2×2.2/0.4² = 27.5 ✔
2. `v = 2h/t`：2×2.2/0.4 = 11 m/s = 1100 cm/s ✔
3. `h = v²/(2g)`：1100²/(2×2750) ≈ 220 cm = 2.2 m ✔（用 UE 单位复核，防厘米/米混用）

**可选**：下落重力倍率 1.35 —— UE 没有原生“下落重力倍率”，在角色 Tick 里按 Velocity.Z < 0 切换 GravityScale（1.0→1.35），下落 0.4 s 缩短到 ≈0.34 s。加之前先跑 10 分钟确认“下落太飘”是真的问题。

碰撞与步态：Capsule 半径 34 cm、半高 88 cm（默认），Max Step Height 45 cm，Walkable Floor Angle 45°。**这三个值和白模尺规（步骤 9）必须一致**，否则角色会卡在 44 cm 的台阶上。

#### 步骤 6：角色状态机（1 个枚举，不许布尔堆）

| 状态 | 进入条件 | 退出条件 | 备注 |
|---|---|---|---|
| Idle | 速度 < 0.1 且在地面 | 速度 ≥ 0.1 | 播待机；3 个变体随机 |
| Locomotion | 在地面且速度 ≥ 0.1 | 离地 / 速度归零 | 按速度混合走/跑 |
| JumpStart | 起跳输入被接受 | 垂直速度 ≤ 0 或 0.15 s 超时 | 播起跳蒙太奇，允许空中转向 |
| Fall | 离地且垂直速度 < 0 | 落地 | 土狼时间在此状态计时 |
| Land | 落地且下落速度 > 400 cm/s | 0.25 s 后或再次起跳 | 重落地播翻滚/缓冲；轻落地直接进 Locomotion |
| Hit | 受击（HP 减少） | 硬直时间结束 | 期间禁止输入，但保留缓冲输入 |
| Interact | 交互确认且目标有效 | 交互动画结束或被打断 | 期间锁定移动 |
| Dead | HP ≤ 0 | 不退出 | 只允许“重开/读档”输入 |

实现纪律：

- 一个 `E_CharacterState` 枚举 + 一个 CurrentState 变量，**每帧只允许 1 个状态**。
- 状态的唯一写入口是 Character 蓝图的 `SetState` 函数（带日志），动画蓝图**只读**。
- 反例：动画蓝图里用“播放完成后回调”去改 MovementMode —— 状态被两处写，出问题时无法定位，且引入 2 帧延迟，落地看起来“踩在棉花上”。

#### 步骤 7：动画蓝图、IK Retargeter、Motion Warping（2–3 天）

骨架路线只有一条：**用 UE 自带 Mannequin 骨骼重定向到自己的角色**，不要手 K 新骨骼。

| 环节 | 做法 | 判据 |
|---|---|---|
| IK Rig | 建 IKR_Hero，定义 Chain（脊柱、左/右腿、手臂）与 Retarget Root | Chain 命名与 Mannequin 一致，避免逐根匹配 |
| IK Retargeter | 建 IKRT_MannyToHero，源选 Mannequin，目标选 Hero 骨骼 | 用预览查看 T-Pose 是否对齐；不对齐先改比例，不要改资产 |
| 批量重定向 | 选中动画 → Asset Actions → Bulk Retarget | 一次 ≥20 条；逐条拖拽会在第 3 个资产后开始出错 |
| 动画蓝图 | 1 个 ABP_Hero，状态机 ≤2 层，每层 ≤6 状态；Locomotion 用 BlendSpace2D（速度 × 方向） | 状态数与角色状态机（步骤 6）1:1 对应 |
| Anim Notify | AN_JumpStart、AN_Land、AN_Footstep_L/R、AN_HitWindow | Notify 只负责“发事件”，不直接改逻辑 |
| Motion Warping | 翻越/攀爬/处决时，用 MotionWarping 组件的 AddOrUpdateWarpTargetFromTransform 对齐落点 | 只在 3–5 个交互点用；滥用会让动作看起来被“吸”过去 |

性能与手感：

- 动画蓝图的 Update Animation 勾选线程安全更新（Thread Safe Update Animation），否则角色多时主线程涨 2–4 ms。
- BlendSpace 插值速度 0.1–0.2 s；插太快脚滑，太慢“拖影”。
- 反向运动学只用在脚部贴地与单手扶墙；全身 IK 会让 4 骨武器出现轻微拉伸。

#### 步骤 8：相机（半天）

| 项 | 值 | 说明 |
|---|---|---|
| 结构 | SpringArm（350 cm）+ Camera，挂在角色 Mesh 上方 70 cm | 不要用 Camera 直接跟角色，碰撞处理会变成手写 |
| 碰撞探测 | SpringArm Probes：通道 Camera，Probe Size 12 cm | 不做的话贴墙时相机穿进石头，露出场景内部 |
| 相机抖动 | 受击/重落地用 CameraShake 资产，幅度见 `references/05-打磨与Demo上线.md` 反馈表 | 抖动不超过 0.25 s，超过会晕 |
| 左右偏置 | 不做过肩偏置（无瞄准玩法时） | 加了会让跳跃落点判断偏 40–60 cm |
| 灵敏度 | 鼠标 0.5 / 摇杆 0.7，且必须暴露为设置项（P5 做 UI） | 硬编码是差评常见来源 |

反例：把相机挂到角色骨骼上做“跟头”式相机 —— 起跳落地画面剧烈摇晃，玩家会把“晕”归因为游戏差，而不是相机错。

#### 步骤 9：白模尺规与盲测（3 天，全流程最省时间的一步）

白模只用 Engine Content 的 Basic Shapes（Cube/Cylinder/Plane）+ 一个 1 m 网格材质 M_Grid_1m。所有尺寸用网格数，不目测。

| 项 | 尺寸 | 依据 |
|---|---|---|
| 角色身高 | 180 cm | 与 Capsule 半高 88 + 半径 34 对齐 |
| 台阶高度 | ≤45 cm | 等于 Max Step Height；超过就变成“要跳” |
| 可跳平台高差 | ≤200 cm | h=2.2 m 留 20 cm 落地冗余 |
| 可跳水平间隙 | ≤450 cm | 6 m/s × 约 0.75 s 滞空 ≈ 4.5 m，再留 15% 容错 |
| 门洞宽 | 120 cm | Capsule 直径 68 cm + 两侧各 26 cm |
| 走廊宽 | 240–360 cm | 单人 1.3 倍肩宽；要战斗就 ×2 |
| 最小落脚面 | 120×120 cm | 容忍 ±30 cm 落地误差 |
| 视线高度 | 130–160 cm | 第三人称以胸口 130 cm 为瞄准点，门洞上方留 ≥50 cm |
| 单段节奏 | 60–90 s | 一段“跳 + 打 + 交互”的循环 |
| 单关时长 | 8–12 min | Demo 关 |

**盲测流程（2 小时，3 人，一个人也能执行）**：

1. 只给一张键位卡（WASD / 空格 / Shift / E / 鼠标左键），**不给任何口头说明**。
2. 记录 3 个观察点：① 是否 60 s 内自己跳过第一个缺口；② 在哪个位置停留 >90 s；③ 通过第一个检查点后是否主动往前走。
3. 全程录屏，每 30 s 记一句话，只记“他以为 X 是 Y”，不记主观评价。
4. 结束后问 3 个问题：刚才要去哪？哪里最难？哪个键最不自然？
5. 判据：3 人中 **≥2 人**不看提示通过关键缺口 → 白模通过；≤1 人 → **只改空间，不改操作**（改操作会让上一轮结论作废）。

反例：白模阶段就换上最终美术资产做盲测 —— 玩家被光照和贴图吸引，会绕开空间问题，你得到的是“美术好评”而不是“空间可用”。

#### 步骤 10：G2 自测（每轮末尾都做，30 分钟）

| 动作 | 命令/方式 | 通过标准 |
|---|---|---|
| 出包 | 打包 Development / Win64（命令见第 3 轮步骤 27） | 双击 exe 能进 L_Sandbox，不报 missing asset |
| 手感抽查 | 连续 20 次跳跃 + 落地，开 `stat unit` | 无卡顿、无脚滑、不掉出场景；帧时间波动 <2 ms |
| 数值对照 | 逐条核对步骤 5 的 12 个数与 `docs/06_数值表.csv` | 编辑器里的值 100% 能在表里找到；找不到就补表 |
| 输入回退 | 拔掉鼠标只用键盘 + 手柄各玩 3 分钟 | 所有操作可完成，无“必须用鼠标点”的界面 |

### 第 2 轮（P3）：系统 + 垂直切片 + 高模替换

#### 步骤 11：战斗系统（2–3 天）

判定与数据分离：**判定在动画帧上，数值在数据表里**。

| 资产 | 内容 | 谁改 |
|---|---|---|
| DT_Attack | 攻击名、伤害、前摇帧、判定帧数、后摇帧、取消窗口、硬直等级 | 策划，同步改数值表 |
| DT_Enemy | HP、抗性、受击硬直倍率、掉落物 ID | 策划 |
| DT_DamageType | 伤害类型（钝击/穿刺/能量）× 目标类型倍率 | 策划 |

帧数口径：**一律按 60 fps 折算**。前摇 8 帧 = 0.133 s，判定 3 帧 = 0.05 s，后摇 10 帧 = 0.167 s。动画剪辑才是真相，秒数只是显示单位。

伤害管线（单向、一处扣血）：

`攻击动画 → AN_HitWindow Notify → 球形 Sweep → ApplyDamage → 受击方 ReceiveDamage → 扣血 → 播反馈（hitstop/闪白/音效）→ 死亡检查`

| 规则 | 值 | 为什么 |
|---|---|---|
| 判定方式 | 判定帧内做一次 Sweep，不逐帧 Overlap | 逐帧 Overlap 会重复命中，每帧还多 0.2–0.5 ms |
| 无敌帧 | 0.3 s | 短于 0.3 s 玩家觉得“没判定”；长于 0.5 s 像卡住 |
| 硬直等级 | Light 0.2 s / Heavy 0.5 s / Knockdown 1.2 s | 必须与动画剪辑长度对齐，不能长于剪辑 |
| 扣血权限 | 只有受击方扣血并广播 OnDamaged | 双向扣血会出现“同帧互相打死”的竞态 |

反例：8 个敌人蓝图各自写一遍扣血 + 掉血 UI —— 改一次平衡要开 9 个文件，第 3 周就漏改 2 个。

#### 步骤 12：交互系统（1–2 天）

| 项 | 做法 | 判据 |
|---|---|---|
| 接口 | BPI_Interactable：CanInteract(PC) / OnInteract(PC) / GetPromptText() | 所有可交互物实现同一接口，不写 Cast |
| 检测 | 角色前方 30 cm 处做半径 90 cm 球体 Overlap，取最近的可交互物 | 用射线要求精确瞄准，休闲玩家直接卡关 |
| 提示 | 屏幕中央固定位置显示 1 条提示，不显示列表 | 同时出现 ≥2 条提示 = 玩家不知道该按哪个 |
| 高亮 | 后处理 Custom Depth + Stencil 描边，离开时复位 | 常开 CustomDepth 会让半透明物体渲染错序 |

反例：要玩家把准心在物体上停 0.5 s 才触发 —— 跑动中永远触发不了，玩家会认为“按 E 没用”。

#### 步骤 13：检查点与存档（1–2 天）

`UGameSave : USaveGame` 字段（只增不改顺序）：

| 字段 | 类型 | 说明 |
|---|---|---|
| SaveVersion | int32 | 从 1 开始；**每加字段必须 +1** |
| LevelName | FName | 关卡名，不用关卡对象引用 |
| CheckpointId | FName | 检查点唯一 ID，不是 Actor 指针 |
| PlayerTransform | FTransform | 位置/朝向 |
| HP | float | 读档恢复 |
| CollectedIds | TArray<FName> | 已收集物 |
| OpenedIds | TArray<FName> | 已开启的机关/门 |
| PlayTimeSeconds | float | 供 QA 记录，不参与逻辑 |

| 规则 | 做法 | 为什么 |
|---|---|---|
| 版本迁移 | 加载时 `if (SaveVersion < 2) { 补默认值; }`，迁移集中在一个函数 | 散落的兼容代码 1 个月后没人敢动 |
| 写盘时机 | 只在检查点触发时写 | 每帧/每开门写盘，机械硬盘上会有 0.3 s 卡顿 |
| 备份槽 | 主槽 + `_bak` 槽，加载失败回退 | 断电/崩溃导致的槽损坏无法修，只能回退 |
| 反序列化 | CheckpointId 查表找 Actor，找不到回关卡默认检查点 | 存 Actor 引用 → 读档时已销毁，直接崩 |

#### 步骤 14：UI 与 CommonUI（2 天）

| 界面 | 类型 | 输入模式 | 要求 |
|---|---|---|---|
| HUD | 普通 Widget，不做 CommonUI 焦点 | GameOnly | 血量、交互提示、字幕；不响应鼠标点击 |
| 暂停/设置 | CommonUI ActivatableWidget，放进 WidgetStack | UIOnly + 焦点 | 默认焦点“继续”；方向键能走完全部条目 |
| 过场字幕 | 不可交互层 | GameOnly（跳过键除外） | 只显示文本，不做点击 |

三条硬规则：

1. **输入模式只在一个函数里改**（GameInstance 的 SetUIState），否则会出现“关了菜单角色不能动”或“菜单开着角色在跑”。
2. UI 以 1080p 为基准，最小字号 24 px；4K 用 DPI Scale 自动放大，不要为 4K 再做一套。
3. 手柄必须能完成所有菜单操作，验收时拔掉鼠标走一遍。

#### 步骤 15：音频与 MetaSound（1–2 天）

`SC_Master` 下分 `SC_SFX / SC_Music / SC_UI / SC_Voice` 四条总线，设置页给 4 个滑杆（分别映射到 SoundMix）。

| 用法 | 资产 | 说明 |
|---|---|---|
| 一次性音效（跳、落地、受击） | MetaSound Source（MCS_） | 暴露 PitchRandom ±5%、Volume 参数，避免机械重复 |
| 短 UI 音 | Sound Wave（S_）+ Sound Cue | 直接播，不做随机 |
| 环境/音乐 | Sound Wave + 循环标记；SC_Music 不参与 3D 衰减 | 音乐若衰减会出现“跑两步就听不到” |

衰减与并发：SFX 用 Attenuation（内半径 300 cm 全音量、外半径 1500 cm 归零）；同类音效 Concurrency 上限 4。
反例：所有音效都 2D 播放 —— 玩家听不出敌人方位，被评价为“打击感差”，其实问题在声像。

#### 步骤 16：VFX 与 Niagara（1–2 天）

| 特效 | 触发点 | 预算（单个） |
|---|---|---|
| NS_Footstep_Dust | 脚步 Notify | ≤20 粒子，生命周期 0.4 s |
| NS_Impact_Hit | 命中判定帧 | ≤40 粒子 + 1 个闪光，生命周期 0.25 s |
| NS_Land_Heavy | 重落地 | ≤60 粒子，1 层环形尘埃 |
| NS_Ambient_Motes | 场景氛围 | 1 个系统常驻，粒子 ≤200，不用 CPU 碰撞 |

三条纪律：

1. 特效不做碰撞、不投射阴影（Cast Shadow 关）；一个投射阴影的粒子系统能让 draw call 翻倍。
2. 用 Niagara 的 Fixed Bounds，否则每个特效都会触发一次边界重算，在 20 个同屏特效时主线程抖动。
3. 屏幕空间后处理类特效（受伤红边）用材质参数集（MPC_Gameplay）统一驱动，不要每个 Actor 各建一个动态材质实例。

#### 步骤 17：光照与后处理（2 天，P3 后才做）

顺序固定为：天空光 → 方向光（或局部光）→ 反射 → 后处理。**不要先堆后处理**：后处理会把光照错误盖住，到第 3 轮优化时无法归因。

| 项 | 设置 | 阈值 |
|---|---|---|
| 全局光照 | Lumen，Final Quality | 白模阶段用 Lumen 低档，P3 再切高 |
| 反射 | Lumen Reflection（或 SSR），不允许全关 | 全关后金属材质看起来像塑料 |
| 方向光 | 强度 5–10 lux 量级，阴影距离 8000 cm | 阴影距离每翻倍，阴影绘制成本约翻倍 |
| 静态光 | 只有在大厅/关键演出用静态/固定光，其余全动态 | 静态光烘焙把每次改场景变成 20 分钟等待 |
| 后处理 | Bloom 0.2–0.4、Exposure 固定、Motion Blur 关 | Motion Blur 在 3D 平台跳跃里提高误判率，无特殊需求就关 |
| 体积雾 | 只在 2–3 个关键场景 | 体积雾是 Lumen 场景最常见的性能黑洞 |

判据：同一个场景在无后处理（PostProcessVolume 全关）下“能看清路”，加上后处理只是更好看。看不清说明光照本身错。

#### 步骤 18：过场与 Sequencer（1 天）

| 项 | 做法 |
|---|---|
| 资产 | LS_Intro / LS_Outro，每段 ≤45 s |
| 触发 | Level Blueprint 里用 LevelSequenceActor + Play，不用 UMG 播视频 |
| 跳过 | 任意键跳过，且跳过要等价于“播完”（必须推进同样的游戏状态） |
| 相机 | 过场用独立 CineCamera，结束后切回玩家相机，切回时做 0.3 s 混合 |
| 音频 | 过场音频走 SC_Voice / SC_Music，不占 SFX 总线 |

反例：跳过只 SetTimer 停播放，不推进状态 —— 玩家跳过后卡在“剧情已过但门没开”。

#### 步骤 19：垂直切片验收（G3 的核心动作）

垂直切片 = **1 个完整关卡 + 全部核心系统 + 成品美术**，标准是“换一关也能 3 天做出来”。

| 判定项 | 通过标准 | 不通过怎么办 |
|---|---|---|
| 完整流程 | 从主菜单进关 → 打到 BOSS/终点 → 结算 → 回主菜单，无断点 | 缺的环节就是 G3 的缺口，补完再算过 |
| 美术一致 | 该关的贴图/材质/光照与美术圣经一致，抽查 10 个资产全部通过验收单 | 退回 P3 资产管线，不要用“先凑合”进切片 |
| 可复现 | 换 1 个新关卡白模 → 按同一套流程 3 天内做出可玩版本 | 做不到说明流程还在人脑里，先写进文档 |
| 存档可回 | 中途退出 → 重进能回到检查点，HP/收集物正确 | 存档 bug 一律在 G3 前修，不带到上线 |
| 性能 | 编辑器内 stat unit ≤ 预算 ×1.3（切片允许 30% 超标） | 超标就在本轮优化，别等 P4 |

#### 步骤 20：高模替换（3–5 天，只做一次）

替换顺序按“玩家看到频率”排：主角 → 常走的地面 → 门/机关 → 敌人 → 装饰。

| 检查项 | 做法 | 判据 |
|---|---|---|
| 替换前冻结 | 白模布局打 tag `WB_LOCKED`，替换期间不改空间 | 边换边改布局 = 无法归因“卡住的到底是模型还是空间” |
| 尺寸一致 | 高模 import 后 Bounds 与白模误差 ≤5 cm | 超了会破坏已调好的跳跃距离 |
| 碰撞 | 用简单碰撞体（Box/Capsule）合并，不做逐三角碰撞 | 逐三角碰撞让角色卡在缝里 |
| LOD | 每个资产 3 级 LOD（100%/50%/25% 面数） | 无 LOD 的资产在 4 GB VRAM 机器上会掉到 30 fps |
| 材质 | 统一 Master Material + MI_ 实例，禁止一个资产一个材质 | 材质数直接影响 draw call 与 shader 编译 |
| 光照 | 替换后重跑一次光照检查（步骤 17 判据） | 高模的粗糙度与原白模差异会让场景变暗/反光 |
| 回滚 | 每个资产替换前 commit，出问题回退到上一个 commit | 一次替换 30 个资产不 commit，出错只能全部重来 |

替换后必须重跑步骤 9 的 3 个盲测观察点（不用重新招 3 人，自己按同一路线走一遍即可）：尺寸变了 → 手感判据变了。

#### 步骤 24：性能预算（先写预算，再看数字）

目标：**1080p / 60 fps，基线机器上 1% low ≥ 50 fps**。基线机器型号在 P1 写进技术方案后不再改，否则预算没有分母。

| 指标 | 预算 | 测量方式 | 超了先砍什么 |
|---|---|---|---|
| 帧时间 | 16.6 ms | stat unit 的 Frame | — |
| CPU 合计 | ≤16 ms（Game ≤10 + Draw ≤8） | stat unit 的 Game / Draw | 蓝图 Tick 数量、同屏敌人数、动画更新 |
| GPU | ≤13 ms | stat unit 的 GPU、stat gpu | 后处理 → 阴影 → Lumen 质量 → 体积雾 |
| 1% low | ≥50 fps | Unreal Insights 帧时间曲线 | 卡顿来源见步骤 26 |
| VRAM | ≤4 GB | stat rhi、memreport -full | 贴图尺寸、缺失的 LOD |
| Draw call | ≤2000 | stat scenerendering 的 Mesh draw calls | 材质实例数、合批、隐藏小物件 |
| Shader 编译卡顿 | 0 次 >0.5 s | 打包后首次进关逐段走 | 打开 PSO 缓存预编译 |

**编辑器里的数字比 standalone 高 20–40%**：所有结论以打包后的 Development 构建为准。

#### 步骤 25：测量与优化顺序（固定顺序，不跳步）

测量命令（控制台，按顺序看）：

stat unit → stat unitgraph → stat gpu → stat scenerendering → stat rhi → stat streaming

深度归因用 Unreal Insights：启动参数加 -trace=cpu,gpu,frame,bookmark，在 UnrealInsights 里看 Game 线程 Top 5 热点函数。

优化顺序（**从上到下砍，不跳步**）：

| 顺序 | 砍什么 | 典型收益 | 副作用 |
|---|---|---|---|
| 1 | 后处理：AO 降档、SSR 关、Bloom 阈值收紧 | GPU 1.5–3 ms | 画面变“平”，可接受 |
| 2 | 阴影：距离 8000→5000 cm、级联 4→3、分辨率降一档 | GPU 1–2 ms | 远处无阴影，玩家几乎不察觉 |
| 3 | Lumen 质量档 / Screen Traces 范围 | GPU 2–4 ms | 反弹光变粗糙 |
| 4 | 体积雾、半透明粒子数量 | GPU 1–3 ms | 氛围减弱 |
| 5 | 材质指令数、Overdraw（shadercomplexity 视图） | GPU 1–2 ms | 需要重做材质 |
| 6 | 分辨率缩放 r.ScreenPercentage（**最后手段**） | 与像素数平方成正比 | 画面糊，差评来源 |

反例：一上来把 ScreenPercentage 设成 70 —— 帧数好看了，但真正的问题（200 个动态材质实例）被掩盖，后面加内容立刻崩。

#### 步骤 26：VRAM、卡顿与常见性能坑

| 现象 | 定位 | 修法 |
|---|---|---|
| VRAM 超 4 GB | stat rhi 看 Texture Pool，memreport -full 找最大 10 个贴图 | 贴图上限 2048（主角 4096 例外），禁止 8K |
| 转视角卡 0.3 s | stat streaming 看是否在流送未卸载的子关 | 流送 Volume 重叠区收窄，卸载半径 ≤ 加载半径 |
| 首次遇到某效果卡 1 s | PSO 编译（打包后才有） | 项目设置开启 PSO 缓存并在打包时预编译 |
| 周期性卡顿（每 30 s） | 蓝图 Spawn/Destroy 高峰触发 GC | 对象池复用（弹道/特效各 10–20 个） |
| 同屏 6 个敌人掉 20 fps | stat game 看动画更新开销 | 动画线程安全更新 + 远景敌人更新频率降半 |
| 大世界跑动掉帧 | 未开距离剔除 | 设置 Cull Distance Volume，小物件 3000 cm 外剔除 |

验证方法：打包 Development 构建，用 stat unit 走完整关，记录每 30 s 的 Frame 峰值；连续 3 次波动 <2 ms 才算稳定。

#### 步骤 27：打包（BuildCookRun，每次出包都用同一条命令）

先写一个 build.bat 放在工程根，之后**只跑这个脚本**，不点菜单。命令行打包可复现、可记录、可让 agent 执行：

```
"C:\Program Files\Epic Games\UE_5.8\Engine\Build\BatchFiles\RunUAT.bat" BuildCookRun
  -project="D:\Game\Game.uproject" -noP4 -platform=Win64 -clientconfig=Shipping
  -cook -build -stage -pak -archive -archivedirectory="D:\Game\Build" -utf8output
```

| 项 | 值 | 说明 |
|---|---|---|
| 配置 | 测试用 Development，发布用 Shipping | Development 保留 stat 命令与日志，Shipping 性能更好 |
| 参数 | -noP4 -cook -build -stage -pak -archive | 缺 -stage 只会 cook 不生成可运行目录 |
| 体积控制 | Shipping 加 -nodebuginfo | 可减 30% 以上体积 |
| 记录 | 每次打包在交付单记：版本号、commit、包大小、耗时 | 出问题时能定位“哪个 commit 开始变慢” |
| 冒烟 5 项 | 能启动 / 能进关 / 能存档读档 / 能退出 / 设置项保存 | 缺一项就当打包失败 |

反例：第一次打包留到最后一周 —— 插件冲突、中文路径、缺失资产、shader 编译失败会全部堆在最后 3 天。

#### 步骤 28：版本管理（Git LFS + 三分支）

仓库根 `.gitattributes` 至少包含：

```
*.uasset filter=lfs diff=lfs merge=lfs -text
*.umap filter=lfs diff=lfs merge=lfs -text
*.fbx   filter=lfs diff=lfs merge=lfs -text
*.png   filter=lfs diff=lfs merge=lfs -text
*.psd   filter=lfs diff=lfs merge=lfs -text
*.wav   filter=lfs diff=lfs merge=lfs -text
*.blend filter=lfs diff=lfs merge=lfs -text
```

`.gitignore` 必须含：`Saved/`、`Intermediate/`、`DerivedDataCache/`、`Binaries/`、`.vs/`、`Build/`。

| 规则 | 做法 | 为什么 |
|---|---|---|
| 分支 | main（可打包） / dev（日常） / feature/<名> | 单人也要，回滚成本最低 |
| 提交粒度 | 每完成一个可验证动作提交一次，每天至少 1 次 | 一次提交 30 个资产，出错无法回退 |
| 版本号 | 每次出包打 tag：v0.1.0（P2 末）、v0.2.0（P3 末）、v1.0.0（上线） | 玩家反馈带版本号，能对上构建 |
| 锁定 | .umap/.uasset 用 LFS 锁（lockable） | 两台机器或两个 agent 同时改同一文件 = 冲突无法自动合并 |
| 单文件 | 单个二进制 <100 MB，单次提交 <200 MB | 超限推送失败；限制以 GitHub 官方文档为准 |
| 提交信息 | `feat/fix/docs/test/chore` + 一句中文 | 与 AGENTS.md 的提交约定一致 |

#### 步骤 29：MCP 与编辑器自动化的规范与禁区

前提：**MCP 服务端能力因实现而异**，"能读"不等于"能写"，具体能力以所用服务端的能力清单为准。任何写操作前先确认服务端是否有该工具。

| 等级 | 操作 | 要求 |
|---|---|---|
| 白名单（可直接做） | 只读查询资产/属性/日志、跑自动化测试、打包、截图、跑控制台统计命令、按已验收清单导入资产、改 DataTable 数值 | 记入交付单 |
| 灰区（做完必须人工看） | 新建蓝图/材质/关卡、改项目设置、批量重命名、移动资产目录 | 交付单附影响文件列表 + 截图/录屏 |
| 黑名单（禁止） | 直接改 .uasset/.umap 二进制、删除资产、改 .uproject 插件列表、改引擎/插件源码、两个会话并行写同一资产、执行来路不明的编辑器脚本 | 违反后资产可能损坏且 UE 不报错，直到打包 cook 失败 |

留痕格式（写进 `templates/07_交付单.md` 的“改动”段）：命令原文 → 影响文件列表 → 回滚方式（git 哪个 commit）。

反例：让 agent “帮忙整理 Content 目录” —— 批量重命名断掉 40 个蓝图引用，编辑器里一切正常，打包时 cook 报 40 个 missing asset。

#### 步骤 30：双输入（键鼠 + 手柄）必须同时成立

**目标：键鼠能通关、手柄能通关、切换设备不用重启。**

| 项 | 键鼠 | 手柄 | 验收 |
|---|---|---|---|
| 移动 | WASD | 左摇杆（死区 0.2） | 拔掉手柄仍可走 |
| 视角 | 鼠标 X/Y（灵敏度 0.5） | 右摇杆（0.7） | 两种设备都能 180° 转身 |
| 跳跃/冲刺/攻击/交互 | Space / Shift / 左键 / E | A / B / X / Y | 每个动作都能触发 |
| 菜单 | 鼠标点击 + 键盘方向 | 十字键/左摇杆 + A/B | 拔鼠标可完成所有菜单 |
| 按键提示 | 键鼠图标 | 手柄图标 | 切换设备 0.5 s 内更新 |
| 重映射 | 设置页可改 | 设置页可改 | 重启后仍生效 |

实现要点：

1. **Enhanced Input 只做一套 Action，两套 Mapping Context**：`IMC_KeyboardMouse` 与 `IMC_Gamepad` 都在 PlayerController 注册；设备切换时不用重建输入。
2. **UI 导航**：CommonUI 的 WidgetStack 要设置初始焦点；用 `SetInputModeGameAndUI`，不要只支持鼠标。所有按钮必须能用方向键/摇杆选中。
3. **输入提示图标**：`UI/InputPrompts` 下按动作建两套画刷（键鼠/手柄），由 `UInputDeviceSubsystem` 或自定义 `OnInputDeviceChanged` 事件切换；不要在 UI 里硬编码键名。
4. **重映射与存档**：把映射存进 `USaveGame`，启动时应用；恢复默认要二次确认；冲突键（同一个键绑两个动作）直接拒绝并提示。
5. **测试矩阵**：`docs/10_测试记录.md` 必须分别记录「键鼠全流程」「手柄全流程」「热切换」「重映射」四项，缺一项 `gate release` 不通过。

反例：只做键鼠，手柄映射是空的；试玩时一半玩家第一分钟就退出。另一个反例：UI 只能鼠标点，手柄玩家卡在开始菜单。

#### 步骤 31：资产导入脚本（材质 / 碰撞 / LOD 自动化）

手工在 Content Browser 里逐个设置材质、碰撞、LOD，是 P3–P4 最容易被低估的时间黑洞。用 `scripts/ue_import_assets.py` 把导入变成可重复命令：

```powershell
# 1. 先 dry-run：不打开 UE，只校验清单、路径、note 参数
python <skill>/scripts/ue_import_assets.py --project-root . --dry-run --json

# 2. 在 UE 编辑器里执行（Tools → Execute Python Script，或 UnrealEditor-Cmd）
python <skill>/scripts/ue_import_assets.py --project-root . --report saved/import_report.json
```

资产清单的 note 列用分号写导入参数：

```text
mat=/Game/_Project/Materials/MI_Hero; collision=complex; lod=1; lod_count=3; scale=1.0
```

| 参数 | 取值 | 作用 |
|---|---|---|
| mat | `/Game/...` 材质实例路径 | 导入后设为资产材质 |
| collision | none / simple / complex / use_complex_as_simple | 碰撞生成策略 |
| lod | 1–4 | 期望 LOD 数（导入后校验） |
| lod_count | 1–4 | 自动 LOD 数量（`--auto-lod` 时生效） |
| scale | 0.01–100 | 导入缩放，默认 1.0 |

安全边界：

- 一次最多导入 12 个资产；先 commit，再跑导入；失败只影响单条，不中断整批。
- 脚本对 UE 版本 API 变化做 `hasattr` 降级：LOD 自动生成不可用时只告警，不伪造成功。
- 导入报告（JSON）附在交付单里；没有报告等于没导入。
- 详见 `docs/UE资产导入脚本.md`。

#### 步骤 32：每日截图巡览（5 分钟发现跑偏）

每天让 agent 出 12 张固定机位截图，用 `scripts/daily_gallery.py` 生成巡览页：

```powershell
# UE 控制台：固定机位截图（示例，按实际关卡改机位）

# 生成巡览页
```

- 巡览页不入库（`gallery/` 在 .gitignore），截图原图按需保留。
